# Анализ AS-IS

## 1. Потоки данных (DFD в табличной форме)

| Источник → процесс / хранилище → потребитель | Данные и трансформация |
|---|---|
| Клиент, цифровые каналы, маркетплейсы → Checkout / Order API | Создание или обновление заказа: состав, канал, регион, выбранные доставка и оплата, промокод. Монолит назначает идентификатор, время создания и начальный статус. |
| Order API → Pricing & Promo Logic / Oracle → Order Processing | Цена и параметры промо. Монолит рассчитывает базовую сумму, применяет канальные и региональные правила; при отсутствии результата промо-сервиса использует Oracle package. |
| Order Processing → Oracle | Заказ, сумма, статусы, резервы, служебные и интеграционные записи. Oracle также содержит часть правил, справочников и бизнес-логики. |
| Order Processing → сервис наличия | Запрос проверки наличия и результат проверки, необходимый для оформления. |
| Order Processing → Delivery Gateway / партнёр доставки | Запрос резервирования слота: идентификатор заказа, регион, тип доставки, код партнёра. Результат обогащает заказ подтверждением или переводит его в `DELIVERY_PENDING`. |
| Order Processing → Payment Gateway / провайдер | Идентификатор заказа, сумма, тип оплаты. В ответе создаётся платёжная сессия и ссылка на оплату; её идентификатор сохраняется в Oracle. |
| Order Processing → Oracle staging → .NET service → партнёрские контуры | Запись о заказе для экспортной обработки; .NET-сервис читает общие staging-таблицы и передаёт данные части партнёров. |
| Status Management / Oracle / Async & batch | Статусы, история, технические состояния и задания повторной обработки. Часть переходов выполняется по расписанию или вручную через административные средства; механизм обновления каналов не установлен. |
| Oracle, выгрузки, API и CSV → Python analytics / BI | Данные заказов, статусов, скидок и логистики преобразуются в витрины и отчёты с разной периодичностью. |

## 2. Таблица интеграций

| Поток данных | Способ / протокол | Надёжность, известная из источников | Зависимость при отказе или задержке |
|---|---|---|---|
| Цифровые каналы → Order API | Синхронный вызов; протокол не установлен | Не установлена | Жёсткая для создания заказа |
| Маркетплейсы → Order API | API-взаимодействие; протокол не установлен | Подтверждения и обновления могут задерживаться | Жёсткая для приёма заказа из канала; задержка статуса требует обработки исключения |
| Монолит → promo service / Oracle package | Синхронный вызов; fallback в Oracle | Fallback позволяет продолжить checkout, но может применить упрощённые правила | Мягкая для доступности checkout, но значимая для корректности цены и промо |
| Монолит → Oracle | Репозитории, прямой SQL и Oracle-процедуры в длинной транзакции | Повторы и SLA не установлены | Жёсткая: без записи и служебных данных нельзя надёжно принять и обработать заказ |
| Монолит → сервис наличия | Преимущественно синхронный вызов при создании заказа; протокол не установлен | Повторы и таймауты не установлены | Жёсткая для checkout: при задержке страдает оформление |
| Монолит → партнёр доставки | Синхронное резервирование; в контуре также есть смешанные, очередные и batch-потоки | При неуспехе создаётся `RETRY_DELIVERY_QUEUE`; общая семантика повторов различается | Мягкая для принятия заказа, жёсткая для подтверждения слота и обещания срока |
| Монолит → платёжный провайдер | Синхронное создание платёжной сессии | Повторы и таймауты не установлены | Жёсткая для оплаты и подтверждения заказа |
| Oracle staging ↔ .NET service | Общие таблицы Oracle | Повторы и дедупликация для этого потока не установлены | Жёсткая для затронутых партнёрских сценариев; риск скрытой связности через БД |
| Async / batch → Python analytics | Очереди, задания и выгрузки | Единые гарантии доставки для контура не установлены | Мягкая для обработки заказа, жёсткая для своевременности отдельных отчётов |
| Python analytics / BI → Oracle | Прямой SQL, витрины, исторические выборки | Обновление близкое к реальному времени, почасовое или ночное | Мягкая для order flow, но создаёт нагрузку на операционную БД и жёсткую зависимость отчётности от Oracle |
| Support tools → Status Management / Oracle | Административный интерфейс и ручные действия | Формализовано частично | Мягкая для стандартного потока, операционно жёсткая для восстановления зависших заказов |

## 3. Карта зависимостей

| Зависимый сценарий | Компонент / канал | Тип | Последствие недоступности или задержки |
|---|---|---|---|
| Создание и сохранение заказа | Oracle | Жёсткая | Нельзя надёжно создать заказ, записать статус, резерв и интеграционные данные. |
| Расчёт промо | Promo service и Oracle fallback | Мягкая с риском | Checkout продолжается, но итог промо может отличаться от целевого правила. |
| Проверка наличия при оформлении | Сервис наличия | Жёсткая | Задержка сервиса ухудшает checkout; без достоверного результата нельзя надёжно подтвердить доступность. |
| Подтверждение доставки | Логистический партнёр / маршрут | Жёсткая для обещания, мягкая для приёма | Заказ принимается, но слот или срок не подтверждён; запускаются повторы и ручной разбор. |
| Оплата и подтверждение заказа | Платёжный провайдер | Жёсткая | Платёжная сессия не создаётся, заказ остаётся в ожидании оплаты. |
| Партнёрская логистика | Общие таблицы Oracle и .NET service | Жёсткая для затронутого потока | Сбой обмена затрагивает партнёрский сценарий; общие таблицы создают скрытую связность. |
| Восстановление исключений | Batch-процессы и support tools | Операционно жёсткая | Зависшие статусы и неподтверждённые операции дольше остаются без разрешения. |
| Аналитика и отчётность | Операционная Oracle | Жёсткая для текущих отчётов, мягкая для order flow | Отчёты запаздывают или расходятся; тяжёлые запросы ухудшают checkout в пиковые периоды. |

## 4. Сводная таблица трёх измерений

| Взаимодействие | Поток данных | Интеграция | Тип зависимости |
|---|---|---|---|
| Цифровые каналы → Order API | Данные нового или изменённого заказа | Синхронный вызов | Жёсткая: без него заказ не создаётся |
| Маркетплейсы → Order API | Заказы, обновления, статусы | API, детали не установлены | Жёсткая для приёма заказа; задержки создают исключения по статусам |
| Order API → Pricing / Promo | Позиции, промокод, канал, регион → сумма и скидка | Синхронный сервис + Oracle fallback | Мягкая для доступности, значимая для корректности расчёта |
| Order Processing → Oracle | Заказ, статусы, резервы, технические записи | SQL, процедуры, общая БД | Жёсткая: центральное хранилище и часть логики |
| Order Processing → сервис наличия | Проверка доступности товара | Преимущественно синхронный вызов, детали не установлены | Жёсткая для достоверного подтверждения availability при checkout |
| Order Processing → логистика | Данные резервирования → слот / маршрут / статус | Синхронный gateway; далее смешанные механизмы | Мягкая для принятия, жёсткая для подтверждённого срока доставки |
| Order Processing → платежи | Заказ, сумма, способ оплаты → платёжная сессия | Синхронный gateway | Жёсткая для оплаты и подтверждения |
| Монолит → Oracle staging → .NET | Экспорт заказа для партнёрского сценария | Общие таблицы Oracle | Жёсткая для соответствующего партнёрского сценария |
| Oracle / Async → аналитика и BI | Заказы, статусы, скидки, логистика → витрины и отчёты | SQL, API, очереди, batch, CSV | Мягкая для order flow; жёсткая для своевременной и согласованной отчётности |
| Support tools → статусы / Oracle | Технический статус, флаг, комментарий, запрос на повторную обработку | Административные средства и ручные действия | Мягкая для happy path, операционно жёсткая для исключений |

### Выявленные проблемы AS-IS

- Oracle одновременно является операционным хранилищем, местом бизнес-логики, интеграционной шиной и источником аналитики.
- В платформе сосуществуют синхронные вызовы, очереди, batch, общие таблицы, API и CSV без единой семантики надёжности.
- Повторная доставка сообщений и внешние подтверждения могут создавать дубли заявок, зависшие статусы и ручные разборы.
- Нет единой канонической модели заказа: операционные, клиентские и аналитические представления расходятся.

## 5. Артефакты, использованные для восстановления текущего состояния

- Исходная AS-IS-диаграмма дала первичную карту компонентов, внешних участников и известных связей; она использовалась как неполный исходный материал.
- Интервью с бизнесом и поддержкой показали последствия технических проблем для клиентов, операторов и процесса обработки исключений.
- Интервью с техническим лидером, логистикой и аналитикой уточнили фактические механизмы интеграций, распределение логики и зависимости.
- Фрагмент `OrderProcessingService` подтвердил синхронные вызовы, прямую работу с Oracle, fallback промо, резервирование доставки и создание платёжной сессии.
- Анализы интервью из `Task1` и `Task2` использовались как вспомогательное обобщение. Технические выводы сверялись с первичными интервью, кодом и AS-IS-диаграммой.
