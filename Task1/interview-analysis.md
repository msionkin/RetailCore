## Протокол: интервью с бизнес-заказчиком 

| Поле | Фиксация |
|------|----------|
| **Цель встречи** | Понять, почему трансформация платформы стала приоритетом и какие у бизнеса цели, метрики и жёсткие ограничения |
| **Ключевой ответ** | Бизнесу нужна не «переписка системы», а управляемая поэтапная траектория: быстрее и предсказуемее выводить коммерческие изменения без потери устойчивости order flow |
| **Факт** | Простые change request'ы (акция, партнёр, региональная доставка) систематически разрастаются в мини-проекты из-за пересечения модулей, исключений и интеграций |
| **Факт** | Разные функции (маркетинг, операции, финансы) видят одни и те же процессы по-разным цифрам — спор идёт не о решениях, а о «правильных» данных |
| **Факт** | Каналы (сайт, приложение, маркетплейсы) сейчас ведут себя как набор почти независимых веток, а не как вариации одной модели |
| **Факт** | Новые сценарии (партнёры, персонализация, промо) давят на систему; временные обходы становятся постоянными |
| **Ограничение** | Нельзя останавливать бизнес — нет «окна» на большую миграцию; все изменения только поэтапно, с контролируемым риском и откатом |
| **Ограничение** | Полный redesign неприемлем; «архитектурная красота» без реалистичного пути внедрения не имеет ценности |
| **Ограничение** | Нельзя заморозить развитие на год ради стабилизации, но нельзя и бесконечно расширять хрупкое ядро |
| **Ограничение** | Зона checkout, оплаты и обещания по доставке — очень высокий риск; туда только с подготовкой и поэтапно |
| **Риск** | Трансформация, которая на бумаге снижает связность, но добавляет слой сложной оркестрации |
| **Риск** | Команды будут защищать локальные workaround'ы; без согласованной картины проблем разговор превратится в «забрать контроль» |
| **Новая гипотеза** | Проблема двух видов «гибкости»: здоровая (настройка платформы) vs нездоровая (ночные конфиги, ручные обходы, договорённости с конкретными людьми) — сейчас доминирует вторая |
| **Вывод** | Для бизнеса успех программы = стабильнее order flow + быстрее типовые коммерческие изменения + единая картина данных + меньше «героизма» + платформа для новых каналов/партнёров; каждый этап должен иметь измеримую промежуточную ценность и управленческое объяснение |

## Протокол: интервью с поддержкой

| Поле | Фиксация                                                                                                                                                                                                                                                                                                         |
|------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Цель встречи** | Понять, где платформа больше всего бьёт по клиентскому опыту и что мешает поддержке закрывать обращения без эскалаций                                                                                                                                                                                            |
| **Ключевой ответ** | Главная боль — расхождение между обещанным при оформлении (цена, срок, статус) и тем, что происходит дальше; прозрачность часто важнее самого сбоя                                                                                                                                                               |
| **Факт** | Топ обращений по платформе: «не понимаю, что с заказом»; «статус не меняется / меняется странно»; «дата доставки изменилась»; «частичная отмена без объяснения»; проблемы с оплатой и возвратом                                                                                                                  |
| **Факт** | Карточка заказа не является единым источником правды — при нестандартном кейсе оператор идёт в соседние интерфейсы, комментарии, админки, логи                                                                                                                                                                   |
| **Факт** | В личном кабинете (ЛК), письме, у оператора и в логистике часто четыре разных «реальности» по одному заказу                                                                                                                                                                                                      |
| **Факт** | Значительная часть практики поддержки держится на опыте людей (тимлиды, маркетплейс-специфика), а не на формализованных правилах в системе                                                                                                                                                                       |
| **Факт** | На пиках растёт не только объём, но и доля «сложных» заказов (маркетплейсы, промо, split shipment, повторные оплаты)                                                                                                                                                                                             |
| **Ограничение** | Поддержка не может напрямую менять состояние заказа — только через ограниченный набор админ-инструментов и эскалацию в смежные команды                                                                                                                                                                           |
| **Ограничение** | При трансформации нельзя терять прозрачность на переходе — временное ухудшение наблюдаемости сразу отразится на обращениях                                                                                                                                                                                       |
| **Риск** | Проектирование только по happy path: на диаграмме всё красиво, а поддержка живёт в отклонениях (зависшие статусы, split shipment, расхождение контуров)                                                                                                                                                          |
| **Риск** | Один «простой» вопрос клиента внутри может быть цепочкой из 5–6 причин (логистика, платёж, ручная проверка, маркетплейс, наличие, задержка витрины статусов)                                                                                                                                                     |
| **Новая гипотеза** | Поддержка — «ручной адаптер» между сложной внутренней системой и клиентом; архитектурная неоднородность напрямую увеличивает стоимость эксплуатации                                                                                                                                                              |
| **Новая гипотеза** | Разрыв между клиентским статусом и внутренним состоянием — системная причина и эскалаций, и недовольства; нужны две модели: абстракция наружу, детализация внутрь                                                                                                                                                |
| **Вывод** | Для поддержки приоритет не «добавить ещё функций», а единая история заказа для оператора, нормализованные статусы с причинами отклонений, автоматическая маршрутизация исключений; система должна уметь объяснять результат, иначе поддержка компенсирует архитектурные пробелы людьми — и это не масштабируется |

## Сводные выводы по итогам сопоставления

**1. Одна проблема — два проявления.** Бизнес описывает неоднородность платформы через предсказуемость изменений и управляемость данных; поддержка — через клиентский опыт и операционную стоимость. Это не противоречие, а два среза одной системной проблемы: отсутствие единой модели заказа и событийного слоя.

**2. Прозрачность — сквозное ограничение программы.** Любой этап трансформации должен сохранять или улучшать наблюдаемость для клиента, оператора и управленческих функций. 

**3. Happy path недостаточен.** Зависшие статусы, split shipment, частичные отмены, маркетплейсы, повторные оплаты — не edge cases, а операционная норма, которую архитектура должна поддерживать явно.

**4. Ограничения релиза (из частично подтверждённых гипотез):**
- Только поэтапная трансформация без остановки бизнеса.
- Критичный контур checkout/оплаты/обещания — изменения только с подготовкой, откатом и усиленным мониторингом.
- Унификация каналов — начинать с типовых, а маркетплейсы и сложные партнёрские сценарии — отдельный путь с формализацией правил.
- Каждый этап — с измеримой промежуточной ценностью для бизнеса и поддержки.
- Двухуровневая модель статусов: абстракция для клиента, детализация с причинами для внутренних пользователей.

**5. Критерий готовности архитектурного решения.** По каждому заказу система (и оператор через неё) должна отвечать на три вопроса: где заказ сейчас, что будет дальше, почему произошло отклонение. Это требование поддержки совпадает с бизнес-целью «единой доверенной картины данных».
